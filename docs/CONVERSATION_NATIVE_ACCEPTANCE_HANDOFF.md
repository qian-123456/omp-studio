## 5. 受控输出怎么推进，哪些操作不能冒充用户发送

实际问题只能通过**原生 UI 输入和发送**进入系统。不得用直接 RPC、脚本改 store、Inspector JS、替换 JSONL 或追加控制文件的方式制造用户消息，然后算原生发送通过。预置父会话记录只用于继承上下文，不是侧聊自有首问。

受控 CLI 默认无限 hold，不会自动回答。原生发送被实际接受后，才能使用输出控制器：

- 控制器：`fixture/tools/control.py`；调用格式见 `fixture/handoff.json` 的 `controls.syntax`。
- 从 `fixture/logs/processes.jsonl` 和 `fixture/logs/rpc/<pid>.jsonl` 读取**实际** session UUID／prompt ID／进程；不要把父会话 ID 硬套到新 fork 的侧聊。
- `delta`：追加实际流式回答片段，保持 working。
- `finish`：追加指定终局文字并结束当前请求；已有接受队列可能开始下一项，但不会自己给下一项答案。不要重复追加整篇已有答案而人为制造重复。
- `pending-on`／`pending-off`：仅在明确验证后台工作与 settled 边界时使用，不制造 prompt。
- 这些控制只指定输出时间和文字，不能写输入或图片。没有看到 UI 产生的真实 prompt／agent_start，不得提前 release。

关键契约：

1. `get_state` 正确包含 `isSettled`、`hasPendingAsyncWork`、`queuedMessageCount`。
2. 消息 ID 稳定，流式、终局与持久历史正确接管。
3. prompt 接受响应与后续 `prompt_result` 关联同一请求；不要再使用不存在的成功状态 `ok`。
4. `agent_end` 不等于 settled；最终 yield 的 `prompt_result` 在 `session_settled` 之前。后台工作或队列未结束不能假空闲。
5. 同步 builtin 以 `agentInvoked:false` 完成本次，不另造 prompt_result，也不把整个会话标空闲。
6. 未知命令必须明确失败，不允许通用空成功。发现具体契约错误只修私有 fixture，递增 revision／冻结 hash，保留旧失败；不能弱化业务断言或伪造成产品通过。

## 6. 七项待验收场景：按此顺序推进

所有场景当前都是 **NOT RUN**。先做侧聊首问与历史，不要先消耗时间完善附件工具。每项都要有实际动作、UI 前后读回、对应受控 RPC／历史证据，以及明确通过／失败／未执行状态。

### 6.1 SIDE_FIRST：首问保留和继承隐私，最高优先级

1. 原生 UI 打开预置项目和主会话，使用当前界面的真实侧聊入口；不得脚本直接创建用户消息。
2. 发送 `fixture/handoff.json` 中的侧聊首问标记：`SIDE_FIRST_OWN_20261110：请只回答这条侧聊问题。`
3. 输出保持 hold。确认实际 fork UUID／文件／进程与实际首个 prompt；线上文本可以带应用的侧聊模板，不应误要求等于裸输入字符串。
4. 在回答完成前，实际查看侧聊区域截图和消息控件：自己的问题应已经出现，不能消失或跑进暂存队列。
5. 用控制器释放对应侧聊的受控答案；首问和答案在最终历史接管后各一份。
6. 父标记 `PARENT_USER_HIDDEN_20261110`、`PARENT_ANSWER_HIDDEN_20261110` 不得作为侧聊自有历史显示。**只对侧聊消息区域做隐私断言；主会话仍在自己区域显示父消息是合法的，不能以全窗口包含父标记判泄露。**
7. 磁盘仍有继承记录是正常的，不能靠删掉父记录或过滤夹具输出来假装隐私修复。

首条真实消息一旦有结果，就向用户报告具体通过点或失败点，不再只有准备进度。

- 上项真实首问完成后，通过原生 UI 关闭侧聊面板，再使用受支持历史入口重开。
- 自己的问题、受控答案各一份；父继承内容仍不暴露；不因 live → history 接管消失或复制。
- 不重发首问，不重置数据，不通过直接修改历史文件制造恢复。记录实际会话 UUID、可见计数和磁盘／RPC 对应关系。

### 6.3 SIDE_ATTACHMENT：已提交 A 只消费一次，新草稿和 B 归属不丢

- 使用真实添加图片入口选择自有红色 A，发送侧聊后续问题；保持受控输出待决。
- 在对应期间编辑新的未发送文字，加入蓝色 B。确认第一笔实际输入只带 A，B 没有被提前送走。
- 旧请求完成后，新文字和 B 保留；下一次真实发送不重新带 A；历史只有已发送的对应附件。
- 分清 RPC 接受完成与模型回答终局，记录新草稿是在什么阶段加入的。没有覆盖提交仍待决的窗口，就不能宣称覆盖了全部异步消费竞态。
- 图片转换可能改变编码；比较实际提交和送达图像，不凭原文件 hash、图片序号或输入 hash 猜归属。
- 添加图片走原生文件选择，不以预置用户消息、拖放脚本或 DOM 注入代替。若官方受支持路径和一个支持的替代均失败，停止附件路径并继续独立文字场景，明确附件仍未验。前台键鼠授权也不等于剪贴板授权。

### 6.4 MAIN_STREAM：真实主聊发送、增量、终局历史

- 真实主聊输入并点击发送，记录唯一实际输入及 prompt ID。
- 释放部分 delta，观察 working、回答增长及自己的问题；随后 finish，观察真实终局／settled。
- 转为历史后问题、答案各一份，已显示的回答不能被短历史吞掉；不能把 message_end 或 agent_end 单独当全会话空闲。
- 若专测后台未完成状态，用既有 pending 控制，不能造不合法事件来得到想要的 UI。

### 6.5 MAIN_STOP：非空部分回答停止后保留

- 新的真实输入，释放非空部分回答，在 native UI 点击停止。
- 用实际 abort／生命周期日志确认停止作用于目标会话；部分回答保留，并有产品规定的停止状态。
- 等待历史接管后仍保留，不能被迟到帧复活／清空；不要用 fixture 主动 finish 冒充点击停止成功。

### 6.6 MAIN_QUEUE：工作期间排队、真实发送或恢复、版本归属

- 主会话实际 working 时，通过真实 UI 暂存／排队多个可区分输入，观察真实队列条目。
- 按当前产品入口验证发送／合并或支持的恢复，记录每个实际提交版本、输入次数、对应图片以及队列删除目标。
- 区分本地暂存与引擎已经接受的队列，不能把 echo 或自动 drain 重复算发送；异步完成不能删除后改内容或另一个稳定 ID。
- 保留现有“新输入在前，再合并暂存”的策略。FIFO／拆成独立回合不是本轮修复授权；本地删除和上游撤回的去向也尚有产品决策，不拿未决定的统一语义当失败标准。

### 6.7 SWITCH_RECOVER：工作期间切换和返回

- 某一实际会话正在流式时，通过原生 UI 切换到另一个自有会话或主／侧区域，再返回。
- 当前回答、问题、历史和未发送草稿分别属于正确会话；迟到结果不跨会话覆盖，没有重复和已显示后缀丢失。
- 使用真实当前进度／历史读回证明恢复，不通过重播同一 prompt 代替重连。未知送达不自动重发。
- 当前夹具 `idleSuspendMinutes:0`，因此这种切换不自动证明“闲置暂停后的冷恢复”或应用重启恢复；未实际覆盖的子场景必须单独列为未测。
